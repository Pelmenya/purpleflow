# План серверного режима PurpleFlow

Рабочая база — серверный режим S1. Один PR соответствует одной фазе. Порядок карточек внутри фазы — порядок исполнения. Проверки используют node:test, tsx и существующий Playwright проекта.

## Фазы реализации

### Фаза 0: Барьер покрытия серверного модуля (S1)

**Цель:** Гейт проекта и CI падают, если код серверного режима покрыт тестами ниже порога.

**Затрагивает:** devops

**Задачи:**

- [ ] 0.1 (#1). Порог покрытия серверного модуля. Порог покрытия ставится до серверного кода, чтобы каждая карточка Ф1–Ф5 видела его в своём последнем шаге `npm run check` и закрывала пробел там, где его создала. Создать core/scripts/coverage-server.ts (запуск через tsx, как core/scripts/check-agents.ts). Константы в начале файла: LINES = 85, BRANCHES = 75, FUNCTIONS = 85 (решение владельца 23.11). Аргумент `--root <каталог>` задаёт корень пакета, по умолчанию — каталог core (на уровень выше scripts). На платформе, отличной от linux, скрипт печатает «Покрытие серверного модуля: пропущено — серверные тесты идут только на Linux» и завершается кодом 0: серверные тесты с сокетом и процессом службы там пропускаются, и покрытие было бы ложно низким. Тесты — файлы <root>/src/server-*.test.ts (fs.readdirSync, без рекурсии, по шаблону /^server-.+\.test\.ts$/); модули — все *.ts под <root>/src/server рекурсивно, кроме *.test.ts и src/server/main.ts (точка входа исполняется в дочернем процессе службы, встроенное покрытие её не видит). Нет ни тестов, ни модулей — печатается «Покрытие серверного модуля: серверных тестов нет» и код 0 (начальное состояние Ф0). Модули есть, а тестов нет — «Покрытие серверного модуля: серверные модули без тестов» с их списком и код 1: удаление всех серверных тестов не отключает порог. Иначе spawnSync(process.execPath, args, { cwd: root, stdio: 'inherit' }), где args: `--enable-source-maps`, `--import` с URL загрузчика import.meta.resolve('tsx'), затем по одному `--import` с file URL (pathToFileURL) каждого модуля, затем `--test --experimental-test-coverage --test-coverage-include=src/server/**/*.ts --test-coverage-exclude=src/server/main.ts --test-coverage-exclude=src/**/*.test.ts --test-coverage-lines=<LINES> --test-coverage-branches=<BRANCHES> --test-coverage-functions=<FUNCTIONS> --test-reporter=spec --test-reporter-destination=stdout --test-reporter=lcov --test-reporter-destination=<временный файл lcov в os.tmpdir()>` и список тестов. Встроенные пороги применяются к сводному покрытию, поэтому маленький непокрытый модуль среди больших покрытых их не роняет: после дочернего процесса скрипт разбирает lcov (записи SF:, LF:/LH:, BRF:/BRH:, FNF:/FNH:, end_of_record) и применяет те же пороги 85/75/85 к каждому учитываемому файлу; метрика с нулевым знаменателем (LF, BRF или FNF = 0) пропускается. Файл ниже порога печатается строкой «Покрытие серверного модуля: файл ниже порога — <путь>: строки N%, ветви N%, функции N%», и скрипт завершается кодом 1. Так ловится и модуль, частично исполненный предзагрузкой (выполнен верхний уровень, функции не вызваны). Предзагрузка каждого модуля обязательна: модуль, который не импортирует ни один тест, иначе в отчёт не попадает и порог проходит (проверено на Node 22/24, 23.11). `--enable-source-maps` обязателен: без него покрытие через tsx показывает 100% для невызванной функции (проверено 23.11). Итог: код 1, если дочерний процесс завершился ненулевым кодом, status null (сигнал) или в lcov есть файл ниже порога; иначе 0. Модуль только с типами даёт нулевые знаменатели и не проверяется: покрывать в нём нечего. Временный файл lcov удаляется в finally. Подключение: в core/package.json скрипт `coverage:server`: `tsx scripts/coverage-server.ts`; в корневом package.json скрипт `coverage:server`: `npm run coverage:server -w @purpleflow/core` и в скрипте `check` перед `npm test` — `npm run build:core && ` и в конец — ` && npm run coverage:server`; в .github/workflows/ci.yml в job check перед шагом `- run: npm test` — шаг `- run: npm run build:core`, а после него — шаг `- run: npm run coverage:server` (на Windows и macOS скрипт сам пропускается). Сборка в check и CI нужна процессным тестам Ф1–Ф5: они запускают core/dist/server/main.js, а dist в Git не хранится и job build артефакты в job check не передаёт. В CONTRIBUTING.md в разделе «Перед PR» — одна фраза: `npm run check` на Linux проверяет порог покрытия серверного модуля (85/75/85), отчёт и непокрытые строки — `npm run coverage:server`. Отвергнуто: порог в конце Ф5 — последняя карточка дописывала бы тесты за четыре фазы чужого кода; порог на всё ядро — правка инфраструктуры проекта вне серверного режима, отдельный PR; c8 или nyc — новая зависимость при встроенном покрытии Node; отдельный шаг только в CI — исполнитель узнал бы о недоборе после PR, а гейт Ralph его не видел бы; прогон всего набора ядра под покрытием — удваивает время check; только сводные пороги — непокрытый модуль тонет в общем проценте; правило «LH = 0» вместо порога по файлу — модуль с исполненным при загрузке экспортом и невызванной функцией проходил бы; порог по файлу без пропуска нулевых знаменателей — модуль только с типами ложно ронял бы порог; код 0 при отсутствии тестов, но наличии модулей — удаление тестов выключало бы порог; процессные тесты без сборки в check — на чистом checkout они падают на отсутствующем core/dist; исключение файлов или комментарии node:coverage ignore ради порога — порог перестаёт что-либо значить. Проверка: core/src/coverage-gate.test.ts: недопокрытый, непротестированный и нулевой среди покрытых модули роняют порог, модули без тестов роняют его, покрытый код проходит; npm run check и CI собирают ядро и вызывают coverage:server

**Когда готова:** Гейт проекта и CI падают, если код серверного режима покрыт тестами ниже порога. Наблюдаемые исходы проверяются сценариями задач выше и полным гейтом `npm run check`.

### Фаза 1: Вход и обзор серверных проектов (S1)

**Цель:** Владелец в двух независимых браузерах видит один серверный каталог.

**Затрагивает:** core

**Задачи:**

- [ ] 1.1 (#2). Ядро: допуск проектов и остановка службы с заморозкой записи. Добавить в CoreOptions (core/src/runtime.ts) необязательный предикат `allowProject?: (projectPath: string) => boolean`. Без предиката допускаются все проекты: desktop и существующие тесты не меняются. Предикат получает projectPath так, как он сохранён в индексе; канонизацию realpath делает вызывающий (#3); исключение предиката означает «не допущен». engine.recover: запись, для которой предикат вернул false, пропускается до существующего цикла по runProcessGroups(s.id) из core/src/run-processes.ts (прогон, server, preview, visual-cleanup и фоновые manager, summary, map, learn; перечень не дублировать) — её PID, run.json и индекс не меняются. engine.pump: кандидаты из очереди фильтруются тем же предикатом, недопущенная запись остаётся queued. engine.activeCount считает только допущенные записи running: чужой running после recover не занимает место в очереди разрешённых. engine.start проверяет предикат первой строкой — до getSettings, k.tools, git, resolveReview и saveAttachments: недопущенный projectPath — отказ «Проект не допущен службой», ни записи, ни вложений, ни snapshot-коммита, ни агента.

Остановка службы — заморозка (решение владельца 23.11). В Kernel (core/src/kernel.ts) добавить публичные поля `closing: boolean` (начально false) и `pending: number` — счётчик принятых вызовов Orchestrator (начально 0); на closing опираются #8, #14 и #15. `Orchestrator.shutdown(): Promise<void>` — обычный, не async метод: первый вызов создаёт и сохраняет Promise, повторные возвращают тот же объект. Он ставит k.closing = true, синхронно ставит `scope.stopped = true` — барьер запуска процессов этого ядра (ниже, «Барьер запуска») — и k.cancelBackground(id) для каждой записи k.store.list(), затем killAll и повторяет killAll каждые 100 мс, пока k.pending больше 0 или не пусто хотя бы одно из k.driving, k.preparing, k.chatBusy и k.managerBusy (не больше 100 кругов, затем запись в trace), после чего делает финальный killAll. Kernel.backgroundCurrent (core/src/kernel.ts) дополнительно возвращает false при closing: фоновые вызовы вне цикла стадий — learn, сводка изменений, карта файлов, менеджер (core/src/run-processes.ts → backgroundProcessGroups) — после ожидания k.tools или ответа агента не пишут projects.json и другие файлы и не запускают следующий шаг; токены старого ядра остаются недействительными и после создания нового Orchestrator. shutdown не входит в CoreApi и CORE_METHODS: окно его не вызывает, desktop продолжает использовать killAll.

Барьер запуска: core/src/proc.ts экспортирует `spawnScope = new AsyncLocalStorage<{ stopped: boolean }>()` из node:async_hooks. Функция run (и exec поверх неё) первой строкой читает spawnScope.getStore(); при stopped === true процесс не порождается, и run сразу возвращает RunResult с code: null, signal: null, пустыми stdout и stderr, timedOut: false, killed: false, durationMs: 0 и spawnError «Служба останавливается»; exec поэтому бросает ошибку. Без хранилища (desktop, существующие тесты) поведение прежнее. Orchestrator создаёт свой объект `scope = { stopped: false }` и выполняет внутри `spawnScope.run(scope, …)` тело конструктора (включая recover и pump) и тело каждого публичного метода — dispatch, sendChat, compactChat, chatToTask, allowChatMcp, askManager, resolveManagerAction, startPreview и остальных. Контекст AsyncLocalStorage переносится через await, промисы и setTimeout, поэтому все процессы, порождённые ядром позже, — агенты, git (включая `git add -A -N` в Git.diffText из фоновой сводки и карты файлов), openspec, команды проверки, серверы предпросмотра, служебные агенты, автопилот после паузы — видят объект своего ядра. Места вызова run не меняются. Единственное исключение — spawnSync login-shell в env.ts при старте. Модульные кэши, общие для ядер одного процесса, хранят только успешный запуск. Таких кэшей в ядре два: majors в core/src/agents/opencode.ts (opencodeMajor) и modelsCache в core/src/services/connection.ts (listOpencodeModels); остальное модульное состояние результата запуска не хранит. Успех — `code === 0 && !killed && !timedOut && !spawnError`. Любой другой исход — отказ барьера, процесс, убитый killAll при shutdown, таймаут, ненулевой код — даёт запасное значение (версию 1, пустой список) только текущему вызову и удаляет из кэша именно созданную запись с проверкой тождества: `if (majors.get(bin) === hit) majors.delete(bin)` и `if (modelsCache.get(key)?.list === list) modelsCache.delete(key)`. Ожидающий промис в кэше разделяется между вызовами как раньше: если он завершится неуспехом, запасное значение получат и ожидающие, но запись удалится, и следующий вызов любого ядра повторит запрос. Иначе принятый вызов старого ядра после shutdown закэшировал бы версию 1 навсегда (новое ядро запускало бы opencode 2 с удалёнными флагами --dir и --pure) или пустой список моделей на минуту. Общего флага процесса и resumeSpawning нет: новый Orchestrator в том же процессе получает новый объект scope и запускает процессы, а принятый вызов старого ядра, проснувшийся после ожидания k.tools, opencodeMajor или очереди serialized, видит stopped своего ядра и остаётся запрещённым навсегда. Поэтому побочный эффект не возникает, даже если shutdown вышел по лимиту кругов с непустым pending, и проверки closing перед отдельными запусками не нужны.

Заморозка записи охватывает все каналы ядра: при closing Kernel.save, Kernel.markStopped и Kernel.fail сразу возвращаются до любых изменений в прогоне, Kernel.log не пишет журнал, Kernel.emit не рассылает событие; функция save в core/src/services/chat.ts и publish в core/src/services/manager.ts при k.closing тоже ничего не пишут и не рассылают (иначе finally askManager после убитого агента записал бы manager/<id>.json и manager.updated). PID-файлы по-прежнему ведёт proc.ts: удаление PID завершённого процесса безопасно для recover, это явная оговорка заморозки. На диске остаётся последнее состояние до closing: у активного прогона — running с попыткой в статусе running, и следующий engine.recover возвращает попытку и ставит прогон в очередь по существующим правилам. Поэтому агент или команда проверки, оборванные killAll, не превращаются ни в stage_failed, ни в красные проверки, ни в «Остановлено пользователем», а остановки стадий (no_checks, plan_invalid, checks_red) во время closing не финализируют прогон.

Отказ заморозки типизирован: core/src/kernel.ts экспортирует `class ShuttingDownError extends Error` с текстом «Служба останавливается», и все отказы заморозки бросают именно его — входы Orchestrator, завершение вызова при closing, повторная проверка в engine.start и проверка в engine.deleteRun; #7 и #8 различают его через instanceof, а не по тексту. Приём и запуск: при closing Orchestrator отклоняет ошибкой ShuttingDownError dispatch, sendChat, compactChat, chatToTask, allowChatMcp, askManager, resolveManagerAction и startPreview; decideExpected, который добавит #8, отклоняется так же. Каждый из этих методов на входе увеличивает k.pending и уменьшает его в finally; если вызов завершается, когда k.closing уже true, метод бросает ShuttingDownError вместо результата, даже если внутренняя операция «удалась»: при заморозке её итог не сохранён (так run.start не вернёт runId несохранённого прогона, а решение — ok без записи). engine.start повторно проверяет closing после предварительных ожиданий (getSettings, k.tools, git, resolveReview) — до saveAttachments и первой записи: отказ ShuttingDownError без записи и вложений. engine.deleteRun после предварительных ожиданий (k.tools, git) и непосредственно перед удалением worktree, файлов и store.forget при closing бросает ShuttingDownError — запись, индекс и backup остаются. Остальные методы Orchestrator служба не вызывает. engine.pump проверяет closing в начале каждой итерации цикла и при closing выходит, даже если уже запущен; engine.launchQueued первой строкой при closing выходит, не меняя прогон; Kernel.checkStop бросает StopSignal и при closing, поэтому цикл engine.drive не начинает следующую стадию или команду; engine.drive первой строкой при closing выходит — до k.driving, k.live и copyEnvFiles, — поэтому запоздалое решение автопилота (autoDecide в core/src/gates.ts ждёт 800 мс вне k.pending) не копирует файлы окружения в worktree после остановки; сама copyEnvFiles в core/src/services/workspace.ts при k.closing первой строкой выходит, закрывая и остальные её вызовы — services/preview.ts → runPreview после ensureOnBranch и prepareWorkspace после записи workspacePending; shutdown дополнительно очищает k.previewLaunches; цикл drive в services/chat.ts при closing не начинает следующий ход — сообщения очереди остаются queued в файле чата. После подготовки рабочей копии engine.start и engine.launchQueued при closing не вызывают drive. catch подготовки в engine.start при closing возвращает run.id без store.forget и без события run.deleted; в launchQueued — выходит без записи и без события. Ручная остановка, не успевшая записаться до closing, не подтверждается: stopActive (#12) отвечает ok только после перечитанного сохранённого stopped.

Известные окна (решение владельца 23.11; общие с выходом desktop, этой задачей не закрываются): остановка сразу после git worktree add и до записи сброса workspacePending — recover повторит подготовку и может остановить прогон с причиной «ветка уже есть»; остановка во время коммита стадии finish — status finished записан до коммита. Фоновый служебный агент, запущенный до closing, завершает killAll, а запуск после stopSpawning невозможен.

Отвергнуто: общий барьер процесса с resumeSpawning в конструкторе — новый Orchestrator снимал бы запрет с принятых вызовов старого ядра (chatToTask и runRole зовут service без owner, и checkOwner после ожидания ничего не проверяет); удаление записи только при spawnError — процесс, убитый killAll при shutdown, возвращает killed: true без spawnError и всё равно закэшировал бы версию 1; ключ кэша по ядру — версия программы от ядра не зависит, и кэш перестал бы работать как кэш; поле gen в RunOptions у каждого вызова run — правка двенадцати модулей без доступа к Kernel (Git, OpenSpec, агенты), карточка не помещалась бы в сессию; проверка closing в каждой точке после ожидания — четыре круга атак находили новую точку; аккуратная остановка с выборочным подавлением записи и ожиданием фоновых задач — четыре круга атак находили новые окна (финиш, git под killAll, автопилот, фоновые агенты), карточка росла до 10 файлов; запись при closing — оборванный агент записывался бы как сбой стадии или красные проверки; фильтрация только в снимке — чужие прогоны всё равно восстанавливаются и запускаются; markStopped при остановке службы — прогон получил бы «Остановлено пользователем» и не продолжился бы сам; проверка allowProject перед первой записью — до неё start уже определяет инструменты, делает snapshot-коммит review и сохраняет вложения; однократный killAll — стадия или чат, вышедшие из ожидания после него, запускают новый процесс; отказ «Служба останавливается» обычным Error — вызывающему пришлось бы разбирать текст сообщения; проверки closing перед каждым запуском (chatToTask, startPreview, runners) — окна после внутренних await у runners (k.tools в runRole и serviceOn) и у opencode (после opencodeMajor) не закрываются, а каждый новый путь запуска потребовал бы своей проверки; только входная проверка closing — вызов, принятый до неё (run.start на k.tools, chatToTask, startPreview, askManager), запускал процесс после последнего killAll, писал файлы и отвечал успехом без сохранённого итога; async-метод shutdown — каждый вызов возвращает новый Promise. Проверка: недопущенный прогон не восстанавливается, не запускается и не занимает место, start отклоняет его первой строкой; shutdown закрывает запуск процессов барьером proc.ts, замораживает запись, не начинает новых стадий и ходов, завершает процессы и оставляет прерванный прогон восстанавливаемым.

Ключ, снова ставший актуальным, — в слушателе onIntentChange и в каждой полной сверке с Host.intents() — переводит запись dropped в pending с nextAttemptAt = now(), нулевой задержкой и очищенным lastError: run.resume после остановки показывает ту же попытку гейта с прежним waitId (#8), и без этого перехода уведомление о нём не пришло бы никогда; delivered не трогается, восстановление failed — только при рестарте. Исход ответа — закрытая таблица, у каждого ответа ровно один исход, сначала по статусу, затем по телу. fetch вызывается с redirect: 'manual': классифицируется исходный статус, а адрес из Location не запрашивается. Любой 4xx, кроме 429, → failed с lastError независимо от тела (пустое, неразборчивое, description: null), причина видна на странице настроек; 429 с конечным положительным числом parameters.retry_after (секунды Bot API) → pending с nextAttemptAt = now() + min(retry_after, 86400) * 1000 (now и nextAttemptAt — миллисекунды; потолок суток держит задержку ниже предела таймера Node 2^31−1 мс и nextAttemptAt конечным и сериализуемым); 429 без такого значения, 5xx, 3xx, 1xx и любой иной код вне 2xx и 4xx, таймаут, сетевая ошибка и сброс соединения → pending с удваиваемой задержкой от 5 секунд до 10 минут, попытки не ограничены; 2xx, тело которого разобрано как объект с ok === true, → delivered, любой другой 2xx (ok: false, null, не-объект, JSON без ok, неразборчивое или пустое тело) → pending с удваиваемой задержкой. Правило неразборчивого тела действует только для 2xx. lastError, результат probe() и status() хранят только санированную причину: HTTP-код, description из тела Bot API, только если это строка, обрезанное до 200 символов, или имя класса сетевой ошибки; URL запроса, сырое тело и цепочка cause не сохраняются, а любое вхождение токена в тексте заменяется на «***». При старте worker после чтения конфигурации все записи failed, ключ которых есть в текущем Host.intents(), переводятся одной атомарной записью в pending с nextAttemptAt = now() и обнулённой задержкой: исправленный токен или chatId вступает в силу после рестарта; failed неактуального ключа становится dropped. Повтор ключа исключён только после сохранённого delivered. Если Bot API ответил 2xx с ok === true, а запись delivered в файл очереди не удалась (ENOSPC, EISDIR или любая другая ошибка writeAtomic), worker помечает ключ отправленным в памяти процесса и до рестарта его больше не отправляет; ошибка записи выводится в stderr санированной, как ошибки доставки. Рестарт в этом случае равен падению до записи delivered: возможен один дубль, как ниже. Возможен дубль, если ответ не получен (таймаут, обрыв) или процесс упал между ответом ok и записью delivered: Bot API не принимает ключ идемпотентности — предел указан на странице настроек и в комментарии модуля. Текст — фиксированная причина по reasonCode (уточнение, утверждение плана, исчерпание попыток или круг ревью, приёмка, остановка с ошибкой) и ссылка. Ссылку строит attentionLink(publicOrigin, intent): wait → /runs/<id>, stopped → /runs/<id>/log; путь обязан проходить isReturnRoute (#4), иначе ошибка генератора. Переход по ссылке только открывает страницу через вход и сессию. Владелец жизненного цикла worker — startService (#6): при наличии раздела telegram он вызывает startTelegram после готовности хоста и до замены обработчика на createServerApp, а в createServerApp передаёт handle через opts.telegram только для маршрутов /settings; createServerApp worker не создаёт. Service.stop сначала ждёт telegram.stop() — сначала флаг остановки, затем вызов функции отписки, возвращённой Host.onIntentChange (#15), снятие таймера сверки, пробуждение worker из ожидания nextAttemptAt (отменяемый таймер задержки: после 429 с retry_after: 300 stop() не ждёт пять минут), abort текущего fetch и ожидание выхода worker; worker проверяет флаг в catch и перед каждой записью очереди, поэтому прерванный abort запрос не записывается обратно в pending и файл очереди после stop() не меняется, — затем host.close(); stop во время startHost закрывает поздний хост без запуска worker. stop() идемпотентен. probe() регистрирует свой fetch в handle с тем же таймаутом 10 секунд и redirect: 'manual'; stop() сначала запрещает новые пробы (они отклоняются «Уведомления останавливаются»), затем abort-ит активные пробы вместе с текущим fetch worker и ждёт их завершения; поздний ответ пробы после stop() статус не меняет. Сбой после готовности хоста — startTelegram бросил (например, битый JSON очереди) или createServerApp — startService перехватывает в try/catch: останавливает частично созданный handle, если он есть, ждёт host.close(), закрывает HTTP-сервер и только затем отклоняет ready; владение dataDir освобождено, и повторный запуск на том же dataDir проходит. Защищённые маршруты: GET /settings — подключён ли Telegram, последняя доставка или ошибка, кнопка пробы; POST /settings/telegram/probe — пробное сообщение и его результат. /settings добавляется в реестр возврата после входа. Без раздела telegram страница показывает «не подключён», ядро и решения работают как прежде. Отвергнуто: dropped навсегда — ожидание, вернувшееся после run.stop → run.resume с тем же waitId, не уведомлялось бы; неотменяемый сон до nextAttemptAt — SIGTERM после 429 ждал бы до 10 минут; проба вне handle — зависший запрос пробы держал бы процесс после host.close и менял бы статус после stop(); исключение слушателя в эмиттер — сбой записи очереди прерывал бы сохранение стадии; worker внутри createServerApp — его handle не доходит до Service.stop, после SIGTERM таймер и fetch живут дальше, повторное создание приложения даёт второй worker; чтение токена после startHost — небезопасный файл обнаруживается только после recover; сырой текст ошибки fetch в lastError — URL /bot<token>/… попадает на страницу; delivered для любого 2xx — ответ ok: false терялся бы; отправка из синхронного слушателя событий — rejected promise роняет службу; гарантия ровно одной доставки — Bot API не принимает ключ идемпотентности, а падение между ответом и записью неустранимо; удержание withRunLock на время отправки ради строгой актуальности — таймаут Telegram задержал бы решение в браузере (O1); failed навсегда — исправленная конфигурация не доставила бы ожидание; retry_after как миллисекунды — лавина запросов; немедленный повтор без сохранённого nextAttemptAt — рестарт после 429 даёт лавину запросов; дедупликация только в памяти — рестарт повторяет доставленное; следование перенаправлениям fetch по умолчанию — 302 на адрес с 200 ok: true стал бы delivered; приоритет неразборчивого тела над 4xx — пустой 400 повторялся бы бесконечно вместо failed; abort без флага остановки — прерванный запрос записался бы в pending уже после stop(); сбой startTelegram без закрытия хоста — каталог данных остаётся занятым до выхода процесса. Отвергнуто: отдельный новый e2e-сценарий — дублирует существующий путь постановки, утверждения и приёмки; требование RED — регресса нет, RED достижим только заведомо неверным ожиданием. Проверка: Существующий сценарий «задача с планом» в чистом профиле без серверных и Telegram-настроек: решения gate1/gate2 в сохранённой истории и run.commit равен HEAD ветки.

**Когда готова:** Из чистого checkout владелец может поднять службу по инструкции и продолжить использовать настольное приложение. Наблюдаемые исходы проверяются сценариями задач выше и полным гейтом `npm run check` и `npm run test:e2e`.

### Фаза 6: Окно приложения в браузере (S1)

**Цель:** После входа браузер показывает оригинальный интерфейс приложения, который работает с ядром на сервере через мост; серверные HTML-страницы удалены.

**Затрагивает:** core / app

**Задачи:**

- [ ] 6.1. Веб-сборка окна. Отдельная точка входа renderer без настольных зависимостей (Sentry для Electron), сборка тех же экранов в статику; служба отдаёт её после входа с политикой безопасности не мягче окна (`app/src/renderer/index.html`). Страница входа — компонентами и стилями окна. Отвергнуто: своя вёрстка серверных экранов — замысел владельца 28.11; копия экранов под веб — расходится с апстримом.
- [ ] 6.2. Транспорт моста. Веб-реализация `window.purpleflow`: `core.*` — `POST /api/core/<метод>` в формате JSON-RPC с сериализацией devalue (байты, `Date`, `undefined`), события — SSE с номером события и полным перечитыванием открытых данных после восстановления. Служба исполняет вызов через серверную обёртку ядра с допуском проектов на каждый идентификатор, путь, результат и событие. Отвергнуто: tRPC — дублирует `CoreApi` и `CORE_METHODS`; socket.io — свой протокол там, где хватает HTTP и SSE.
- [ ] 6.3. Адрес страницы. Навигация окна (`View`) синхронизируется с адресом: экран прогона и журнал имеют свои пути, перезагрузка восстанавливает экран, ссылки Telegram (`/runs/<id>`, `/runs/<id>/log`) открывают нужный экран через вход с возвратом.
- [ ] 6.4. Паритет моста и удаление HTML-страниц. Каждая функция `PurpleFlowBridge` имеет браузерную реализацию или замену; тест контрактов падает при функции без реализации или с разошедшимся контрактом. Серверные HTML-страницы и их тесты удаляются, сценарии S1 проверяются через окно.
- [ ] 6.5. Защита входа. Служба слушает только loopback; cookie `Secure`, `HttpOnly`, `SameSite=Strict`; `Origin` на изменяющих запросах и потоках; 10 неудачных попыток — блокировка на 15 минут; новый токен при входе, абсолютный срок 12 часов, `no-store`; секрет входа — хеш с солью; «Выйти на всех устройствах»; истечение и выход закрывают потоки сессии. Задача стоит в Ф6, потому что Ф7 открывает действия уровня сервера.

**Когда готова:** Владелец входит с телефона и ноутбука, видит интерфейс приложения и проходит постановку, план и приёмку; HTML-страниц нет; полный гейт `npm run check` и e2e окна проходят.

### Фаза 7: Действия и гарантии сервера в окне (S1)

**Цель:** Из браузера доступны все действия приложения в проектах, а гарантии сервера держатся независимо от окна.

**Затрагивает:** core / app

**Задачи:**

- [ ] 7.1. Решение по показанному снимку. План, дифф и запись прогона приходят согласованным снимком с версией ожидания; экраны передают её полем транспортного конверта, служба отклоняет решение без версии или с устаревшей.
- [ ] 7.2. Идентификаторы изменяющих вызовов. Один перечень изменяющих вызовов, сверяемый в CI с мостом; идентификатор в конверте, служба хранит отпечаток запроса и результат; повтор возвращает исходный результат, неизвестный после падения исход — ответ «исход неизвестен», другое содержимое с тем же идентификатором отклоняется.
- [ ] 7.3. Действия прогона и автопилот. Слияние, PR, удаление и восстановление прогона; постановка с автопилотом и выбором режима; уведомление только об ожидании, которое ждёт человека.
- [ ] 7.4. Чат и менеджер на сервере. Чат с правками файлов и с полным доступом; команды оболочки менеджера прогона.
- [ ] 7.5. Настройки и секреты. Настройки службы редактируются из браузера и действуют без перезапуска; секреты хранятся зашифрованными в файлах пользователя службы, ключ шифрования — отдельно от них; браузер получает признак наличия или хвост.

**Когда готова:** Задача из браузера проходит до слияния или PR, в том числе на автопилоте; запоздалое решение и повтор после обрыва не применяются дважды; полный гейт проходит.
