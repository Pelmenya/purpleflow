# Работа в форке PurpleFlow

Прочитай [архитектуру](ARCHITECTURE.md) и [правила вклада](CONTRIBUTING.md) перед изменениями. Здесь `CLAUDE.md` — источник инструкций. После правки выполни `node scripts/sync-agent-docs.mjs`, чтобы обновить `AGENTS.md`.

## Код и проверки

- `core/` — TypeScript-ядро оркестратора. `app/` — Electron и React. Интерфейс обращается к мосту через `app/src/renderer/src/lib/api.ts`. Изменения API окна согласуй между `CoreApi`, `Orchestrator` и `CORE_METHODS`.
- Установи зависимости через `npm ci`. Перед сдачей запусти `npm run check`. Для правок интерфейса проверь затронутый сценарий в `npm run dev`. Сквозные тесты с фейковыми агентами запускаются через `npm run test:e2e`.
- Соблюдай TypeScript `strict`, используй `import type` для типов. Интерфейс, комментарии и названия тестов пиши по-русски. Один PR содержит одно логическое изменение.

## Репозитории и Ralph

- Рабочие ветки, карточки, вехи и PR ведём в `Pelmenya/purpleflow`. `origin` указывает на этот форк. `upstream` указывает на `PurpleSchool/purpleflow` для чтения обновлений.
- Создание PR в `PurpleSchool/purpleflow` — отдельное действие по прямому запросу владельца. При подготовке такого PR переноси продуктовые изменения для PurpleFlow.
- Инструкции для сессий петли находятся в [.claude/ralph/ralph.project.md](.claude/ralph/ralph.project.md). Данные состояния и учётные данные хранятся вне Git.

## Подготовка карточек для Kimi

Исполнитель карточек серверного режима — Kimi. При передаче работы применяй этот порядок самостоятельно. Для резки прочитай проектные скиллы `prd`, `plan-phase` и `issues`. Критическое ревью PRD и атака дизайна карточек — две отдельные проверки.

1. Свяжи каждый критерий PRD с одной задачей плана. Подготовь тела карточек в порядке исполнения. Для Kimi укажи решение, обязательства, границы, карту чтения, 3–6 шагов с командами и ожидаемым результатом, приёмку и предпосылки.
2. Перед публикацией дай Kimi каждое тело отдельно вместе с исходным кодом до реализации. Проверь шаги, существование символов и команд, повтор после сбоя, потерю ответа, устаревшие данные и сочетания обязательств. Отдельным вызовом Kimi проверь композицию каждой фазы: производители и потребители контрактов, порядок и промежуточные состояния. Используй согласованную модель и сохрани фактически выбранный алиас.
3. Сохрани исходные ответы, разбери находки с привязкой к карточкам и внеси принятые изменения прямо в тела. Существенно изменённый контракт повторно отдай на атаку, включая затронутые стыки. Публикуй в форке, когда на это есть разрешение владельца. Свяжи локальные свидетельства с реальными номерами и окончательными телами на GitHub.
4. Перед подтверждением каждой фазы синхронизируй `main` форка с `upstream/main`. Пока в `main` нет своих коммитов, хватает `gh repo sync`. После них вливай апстрим merge-коммитом в отдельной ветке через PR. Вливай последний коммит апстрима с зелёным CI, а не красную вершину. Пока фаза идёт в петле, апстрим не вливай. Сверь якоря карточек фазы с обновлённым кодом. Снова отдай Kimi вместе с композицией фазы только те карточки, чьи якоря, контракты или поведение изменил апстрим. Если файл из карты чтения изменён в другом месте, достаточно сверки без новой атаки, а итог сверки запиши в триаж фазы. Принятые правки внеси в тела на GitHub. Остальные фазы сверяй позже, каждую перед её стартом.
5. До включения в очередь проверь открытые issues вехи, файлы индивидуальных атак, атаку композиции, триаж и наличие предпосылок в базе фазы. Подтверди карточки командой `node scripts/phase-attack.mjs stamp <номер-вехи>`. Штатный боевой старт через `./ralph start` проверяет свидетельства. Само создание вехи не запускает реализацию.

Свидетельства хранятся локально в `.claude/local/attacks/fN/`. Формат описан в `scripts/phase-attack.mjs`. Проектные правила действуют также в Codex. Исходные пользовательские хуки Claude Code на машине владельца — `~/.claude/hooks/cut-skill-barrier.cjs`, `phase-attack-barrier.cjs` и `phase-attack-stamp.cjs`.
